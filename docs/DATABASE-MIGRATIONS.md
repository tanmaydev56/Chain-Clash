# Database migrations

Drizzle migrations in `drizzle/` are the only production schema path. Request
handlers never create or alter tables. Apply them before deploying application
code that depends on them.

## Commands

For a local D1 database:

```powershell
npx wrangler d1 migrations apply <D1_DATABASE_NAME> --local --config dist/server/wrangler.json
```

For the production database, after the production `wrangler.json` has been
generated by `npm run build` and its `DB` binding points at the production D1
database:

```powershell
npx wrangler d1 migrations apply <D1_DATABASE_NAME> --remote --config dist/server/wrangler.json
```

Replace `<D1_DATABASE_NAME>` with the name shown in the Cloudflare D1 dashboard.
Run the remote command exactly once before deploying this version.

`0005_great_invaders.sql` creates `guest_sessions` and adds the non-null
`rooms.state_version` column with a default of `0`. Existing rooms and users
remain usable after it runs. Existing guests do not have a signed session
cookie, so they must start a new guest session; their former anonymous identity
is deliberately not accepted as an authorization fallback.

## Guest session secret

Set the server-only Worker/Sites secret before deployment. Generate it locally
and never commit or paste its value into source control:

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

Save the result as `GUEST_SESSION_SECRET`. Cookies are opaque session IDs signed
with HMAC-SHA-256, `HttpOnly`, `SameSite=Lax`, and `Secure` on HTTPS. They expire
after one year; deleting an account deletes its session rows and clears the
cookie. Rotating the secret intentionally invalidates every existing cookie.
